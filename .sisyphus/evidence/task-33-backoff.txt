## Exponential Backoff Implementation

### Configuration (lines 10-15)

```rust
const BACKOFF_DELAYS: [Duration; 4] = [
    Duration::from_secs(2),
    Duration::from_secs(4),
    Duration::from_secs(8),
    Duration::from_secs(16),
];
```

**Backoff Sequence:**
1. First failure: Wait 2 seconds before retry
2. Second failure: Wait 4 seconds before retry
3. Third failure: Wait 8 seconds before retry
4. Fourth failure: Wait 16 seconds before retry
5. After 4 failures: Reset to normal interval

### Backoff Logic (lines 80-102)

```rust
async fn run_scheduler(&self) {
    let mut backoff_index = 0;
    let mut last_sync_failed = false;

    loop {
        let settings = self.get_settings().await;

        if !settings.enabled {
            // Check every minute if sync is disabled
            sleep(Duration::from_secs(60)).await;
            continue;
        }

        // If last sync failed, use exponential backoff
        if last_sync_failed && backoff_index < BACKOFF_DELAYS.len() {
            let backoff_delay = BACKOFF_DELAYS[backoff_index];
            sleep(backoff_delay).await;
            backoff_index += 1;
        } else {
            // Normal interval
            let sync_interval = Duration::from_secs(settings.interval_minutes * 60);
            sleep(sync_interval).await;
        }
        
        // ... sync logic ...
    }
}
```

### Success Reset (lines 129-136)

match self.perform_sync().await {

## Key Design Decisions

### 1. Why Exponential Backoff?

**Problem:** Constant retry intervals can:
- Overwhelm failing servers
- Waste battery on mobile devices
- Generate excessive error logs

**Solution:** Exponential backoff:
- Reduces load on failing systems
- Gives transient issues time to resolve
- Conserves resources during extended outages

### 2. Why 2s, 4s, 8s, 16s?

**Rationale:**
- **2s**: Fast recovery for transient network blips
- **4s**: Reasonable wait for brief server restarts
- **8s**: Allows time for network reconnection
- **16s**: Final attempt before reverting to normal interval

**Alternative considered:** 1s, 2s, 4s, 8s
- Rejected: Too aggressive for first retry
- 2s gives server/network more breathing room

### 3. Why Cap at 4 Attempts?

**Rationale:**
- After 30 seconds total (2+4+8+16), issue is likely persistent
- Reverting to normal interval prevents indefinite backoff growth
- User can still manually trigger sync if needed

**Alternative considered:** Unlimited exponential growth
- Rejected: Could lead to hours between retries
- Normal interval (15min) is reasonable for persistent failures

### 4. Why Reset on Success?

**Rationale:**
- Transient failures shouldn't penalize future syncs
- Once connectivity restored, resume normal operation
- Prevents "backoff debt" accumulation

## Failure Scenarios Handled

### 1. Network Connectivity Failure
- **Detection:** TCP connect timeout (5s)
- **Response:** Emit "failed" event, trigger backoff
- **User Impact:** Status badge shows "Failed" with "Unable to reach server"

### 2. HTTP Request Failure
- **Detection:** reqwest error (connection refused, timeout, etc.)
- **Response:** Emit "failed" event, trigger backoff
- **User Impact:** Status badge shows "Failed" with error message

### 3. HTTP Non-Success Status
- **Detection:** !response.status().is_success()
- **Response:** Emit "failed" event with HTTP status code
- **User Impact:** Status badge shows "Failed: HTTP 500" (example)

### 4. Server Unavailable
- **Detection:** Network check fails before sync attempt
- **Response:** Skip sync, emit "failed" event, trigger backoff
- **User Impact:** Status badge shows "Network connectivity check failed"

## Code Quality

- `backoff_index`: Tracks current position in BACKOFF_DELAYS array
- `last_sync_failed`: Boolean flag to trigger backoff logic
- Both reset to 0/false on successful sync

### Thread Safety
- Backoff state is local to scheduler task (no shared state needed)
- Settings accessed via Arc<RwLock<SyncSettings>> for thread-safe reads

### Error Handling
- All sync errors captured and emitted to frontend
- Network check failures treated same as sync failures
- No panics or unwraps in scheduler loop
