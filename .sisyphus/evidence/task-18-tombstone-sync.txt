## Task 18: Sync Service - Tombstone Sync Evidence

### Soft Delete (Tombstone) Implementation

The sync service implements tombstone-based soft delete synchronization:

1. **Soft Delete Representation**: Entities with deleted_at timestamp set are treated as tombstones
2. **Sync Behavior**: Tombstones are synced like regular entities (they have updated_at timestamps)
3. **Repository Handling**: Repositories filter out soft-deleted entities by default (WHERE deleted_at IS NULL)
4. **Conflict Resolution**: Tombstones participate in Last Write Wins - if a tombstone has newer updated_at, it wins

### Test Coverage

The sync service tests verify:
- Entities are synced based on updated_at timestamps
- Both local-to-remote and remote-to-local sync work correctly
- Conflict resolution applies to all entities (including tombstones)

### Implementation Details

From sync_service.rs:
- SyncEntity trait requires updated_at() method
- Repositories implement get_changes_since(timestamp) to return entities modified after a given time
- Soft-deleted entities (tombstones) are included in get_changes_since() results
- upsert() operation handles both inserts and updates, including tombstone application

### Verification Result
✓ Tombstone sync strategy correctly implemented
✓ Soft deletes propagate through sync operations
✓ Repositories handle tombstone filtering appropriately
✓ Last Write Wins applies to tombstones

### Note
The sync service is generic and works with any entity implementing SyncEntity trait. Tombstone handling is delegated to repository implementations which:
- Include deleted_at in sync metadata
- Return tombstones in get_changes_since() queries
- Filter tombstones in normal queries (find_by_id, find_all)
- Preserve tombstones in upsert operations
