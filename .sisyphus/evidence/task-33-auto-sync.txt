Task 33: Background Sync Scheduler - Auto-Sync Evidence
========================================================

## Implementation Summary

### Backend: sync_scheduler.rs
- Location: src-tauri/src/infrastructure/sync/sync_scheduler.rs
- Scheduler runs in background tokio task spawned at app startup
- Uses tokio::time::sleep for interval-based triggering
- Default interval: 15 minutes (configurable: 5, 15, 30, 60 minutes)
- Minimum interval enforced: 5 minutes

### Key Features

1. **Configurable Sync Interval**
   - Default: 15 minutes
   - Options: 5, 15, 30, 60 minutes
   - Enforces minimum of 5 minutes to prevent excessive syncing

2. **Enable/Disable Toggle**
   - Settings stored in backend via Tauri commands
   - When disabled, scheduler checks every 60 seconds if re-enabled
   - No sync operations performed while disabled

3. **Network Connectivity Check**
   - TCP connect to 127.0.0.1:3000 before each sync
   - 5-second timeout for connectivity check
   - Fails gracefully if server unreachable

4. **Sync Operations**
   - Calls REST API endpoints: /api/sync/push and /api/sync/pull
   - Push: Sends local changes to server
   - Pull: Retrieves remote changes from server
   - Uses reqwest HTTP client

5. **Event Emission to Frontend**
   - Event name: "sync:status"
   - Statuses: "started", "completed", "failed"
   - Payload includes message and optional error details

### Frontend Integration: SettingsPage.tsx

1. **Sync Settings UI**
   - Location: src/pages/SettingsPage.tsx (lines 264-336)
   - Switch component for enable/disable
   - Select dropdown for interval selection
   - Real-time status display with badges

2. **Event Listener**
   - Listens to "sync:status" events from backend
   - Updates UI with last sync status
   - Shows success (green), syncing (secondary), or failed (red) badges

3. **Settings Persistence**
   - Calls updateSyncSettings() Tauri command on change
   - Loads settings from backend on mount via getSyncSettings()
   - Settings stored in backend state (Arc<RwLock<SyncSettings>>)

## Architecture Decisions

1. **Why tokio::time::sleep instead of interval?**
   - Allows dynamic interval changes without restarting scheduler
   - Scheduler checks settings on each iteration
   - More flexible for exponential backoff integration

2. **Why Arc<RwLock<SyncSettings>>?**
   - Thread-safe shared state between scheduler and Tauri commands
   - Allows runtime updates without stopping scheduler
   - Read-heavy workload (scheduler reads, commands write occasionally)

3. **Why not tauri-plugin-store for settings?**
   - Settings need to be accessible from scheduler (Rust side)
   - In-memory state is sufficient (settings reset on app restart is acceptable)
   - Simpler architecture without file I/O on every sync check

4. **Why check network connectivity?**
   - Prevents unnecessary sync attempts when offline
   - Reduces error noise in logs and UI
   - Triggers backoff mechanism appropriately

## Evidence of Functionality

### 1. Scheduler Loop Logic (lines 80-148)
- Checks settings.enabled before each sync
- Sleeps for configured interval or backoff delay
- Emits events to frontend on status changes
- Resets backoff on successful sync

### 2. Settings Update Flow
Frontend → updateSyncSettings() → SyncCommandState → scheduler.update_settings() → RwLock write

### 3. Event Flow
Scheduler → emit("sync:status") → Frontend listen() → UI update

### 4. Network Check (lines 150-158)
- TCP connect with 5-second timeout
- Returns bool (true = connected, false = offline)
- Used as gate before perform_sync()

### 5. Sync Execution (lines 160-193)
- HTTP POST to /api/sync/push with device_id and changes
- HTTP POST to /api/sync/pull with device_id and last_sync_at
- Returns error if HTTP status not success
