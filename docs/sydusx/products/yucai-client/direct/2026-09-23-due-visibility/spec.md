# 到期事项常显提醒(首页提醒条 + 托盘行 + 收件箱)— spec

> 直落 feature,2026-09-23(无 release;照 v1.0.10 直落先例 + F21 精简走法,spec 落 feature 目录;
> `direct/` 为无 release 直落 feature 的归置先例首立)。
> 来源:brainstorm「三层提醒模型」——用户问「重要到期事项能否常显避免忘记,行业最佳实践如何」,
> 收敛为补被动常显层 + 环境可见层 + 应用内通知中心(收件箱)。grill 六决策见 Grill record。

## 背景与意图

v1.0.10「到期催办提醒」已完成**主动瞬态层**:DueScanner 双源(债务期次 + 信用卡还款日)、
advanceDays/repeatHours 配置化、6h 催办重发、挂失停催、处理完成停催。但**应用内无常显面**——
打开应用看不到任何到期信息,系统 toast 瞬态即逝(Windows 操作中心用户不习惯翻),这正是
「可能会忘」的体验缺口。

行业依据(brainstorm 调研):Mint「Upcoming Bills」/ YNAB「Upcoming」/ Quicken「Upcoming
Bills & Income」= 首页被动常显区块;本地通知 = 主动瞬态;银行端 alerts center = 低量级下
**状态真相驱动、无已读态**的提醒中心。御财量级(月个位数条)与单用户桌面场景映射后:

1. **被动常显层** —— 首页(账户页)净资产 hero 上方「到期提醒条」;
2. **环境可见层** —— 托盘菜单待还行(F25 数据头先例);
3. **应用内通知中心(收件箱)** —— 待处理 + 历史台账(用户 grill #4 辩护进 scope)。

## 需求

### Requirement: FR-1 首页到期提醒条

- [ ] 系统 SHALL 在账户页净资产 hero 上方渲染到期聚合条,当且仅当存在窗口内候选
  (到期日差 ≤ advanceDays 或已逾期,且未被挂失);聚合文案 SHALL 为
  「⏰ N 笔待还 · 最近 X 天后」,存在逾期时 SHALL 优先展示逾期语义(「M 笔已逾期 N 天」合入文案,design 定具体合成形)。

#### Scenario: 有候选显示

- GIVEN 1 张信用卡还款日在 3 天后且欠款 > 0,advanceDays = 3
- WHEN 打开账户页
- THEN 净资产 hero 上方显示聚合条「⏰ 1 笔待还 · 最近 3 天后」

#### Scenario: 逾期优先

- GIVEN 1 笔债务期次已逾期 2 天、1 张卡 3 天后到期
- WHEN 打开账户页
- THEN 聚合条同时反映逾期笔数与最近到期(逾期语义优先呈现)

#### Scenario: 空态不渲染

- GIVEN 无窗口内候选(无到期、或候选全部挂失)
- WHEN 打开账户页
- THEN 不渲染聚合条,净资产 hero 回到页面顶部原位

### Requirement: FR-2 展开明细与着色

- [ ] 点击聚合条 SHALL 展开明细列表(条目 = 名称、金额、到期日/逾期天数),紧迫度着色
  SHALL 承 F37 桶约定(逾期/≤7 天红、≤15 天黄)套用于窗口内条目;再次点击 SHALL 收起。
  默认形态为收起的聚合条。

#### Scenario: 展开/收起

- GIVEN 聚合条可见且收起
- WHEN 点击聚合条
- THEN 展开明细列表,每条含名称/金额/到期信息并按 F37 桶着色
- WHEN 再次点击
- THEN 收起回聚合条

### Requirement: FR-3 条目直达

- [ ] 明细条目点击 SHALL 直达对应处理动作:信用卡条目直开还款对话框
  (showCreditCardRepayDialog 既有链路);债务期次条目直跳该债务详情页。
  候选数据 SHALL 携带强类型路由目标(具体形态 design 阶段定,禁止解析 id 字符串前缀的脆弱契约)。

#### Scenario: 信用卡直达

- GIVEN 展开明细中有一条信用卡候选
- WHEN 点击该条
- THEN 直开该卡还款对话框(全额/最低/分期三方式)

#### Scenario: 期次直达

- GIVEN 展开明细中有一条债务期次候选
- WHEN 点击该条
- THEN 跳转该债务详情页(期次列表可见)

### Requirement: FR-4 托盘待还行

- [ ] 托盘菜单数据头区 SHALL 新增待还行「待还 N 笔 · 最近 X 天后」:永不含金额;
  不适用隐私开关(承 F25「开关管金额不管存在性」哲学,笔数非金额);无候选时该行
  SHALL 不显示;刷新时机 SHALL 复用 F25 既有三触发(watch 防抖 / tick / 窗口 show)。

#### Scenario: 无候选无行

- GIVEN 无窗口内候选
- WHEN 托盘菜单刷新
- THEN 数据头区不出现待还行(不占位)

#### Scenario: 隐私开关不影响

- GIVEN showTrayAmounts = false(金额隐藏)且有 2 笔待还
- THEN 待还行仍显示「待还 2 笔 · 最近 X 天后」(数据头金额两行按既有行为变「金额已隐藏」)

### Requirement: FR-5 收件箱页

- [ ] 应用 SHALL 提供收件箱页(提醒中心):两区布局(待处理置顶 / 历史沉底);条目三态
  (待处理 / 已处理 / 已挂失);「新增小圆点」= 上次看过之后新增的**待处理**条目,
  且 SHALL 仅在待处理区打点(历史是档案不打点);历史 SHALL 永久保留;条目数据 SHALL
  携带类型字段(本期恒「到期提醒」,为未来类型留缝不实现)。

#### Scenario: 小圆点

- GIVEN 上次看过收件箱后新增 1 条待处理候选
- WHEN 打开收件箱
- THEN 该条带新增小圆点;历史区条目无点
- WHEN 再次打开收件箱
- THEN 该条无点(lastSeen 已更新)

#### Scenario: 三态呈现

- GIVEN 1 条待处理、1 条已处理(欠款已清)、1 条已挂失
- WHEN 打开收件箱
- THEN 待处理区 1 条(置顶),历史区 2 条分别标已处理/已挂失

### Requirement: FR-6 状态真相驱动

- [ ] 收件箱条目状态 SHALL 由领域事实驱动更新:候选进入提醒窗口即入箱(upsert,不重复);
  欠款清零/期次 paid → 已处理并沉入历史;挂失 → 已挂失。不引入任何用户手工标状态的动线
  (「不再提醒」挂失动线沿用既有入口)。

#### Scenario: 处理自动沉底

- GIVEN 1 条待处理信用卡候选
- WHEN 用户经还款流程清零该卡欠款
- THEN 该条目自动变已处理、沉入历史区(首页聚合条与托盘行同步消失)

### Requirement: FR-7 入口

- [ ] 收件箱入口 SHALL 为两处:聚合条上「查看全部」动作 + 托盘菜单项;无候选时主窗口
  SHALL 无入口(托盘唯二,历史仍可从托盘进)。

#### Scenario: 无候选仍可达

- GIVEN 无窗口内候选(聚合条不显示)
- WHEN 用户点击托盘菜单收件箱项
- THEN 主窗口打开收件箱页,历史区可见

### Requirement: FR-8 通知零改动

- [ ] 既有系统通知行为 SHALL 逐字不变:advanceDays/repeatHours 配置语义、6h 催办重发、
  桶去重、挂失停催、处理完成停催全部保持 v1.0.10 行为。

#### Scenario: 回归

- WHEN 到期扫描周期运行
- THEN 通知发送行为与 v1.0.10 完全一致(既有 scanner/policy 测试不改断言全绿)

### Requirement: NFR-1 候选零新源

- [ ] 提醒条/托盘行/收件箱待处理区 SHALL 复用 DueScanner 双源(债务期次 + 信用卡)
  同一份候选与挂失过滤,SHALL NOT 新增提醒来源。

### Requirement: NFR-2 双主题

- [ ] 新增 UI SHALL 使用 design-v2 语义令牌(context.yucai),亮暗两主题下均正确
  (照 F4 迁移后规范,零裸色)。

### Requirement: NFR-3 宽窄屏

- [ ] 聚合条 SHALL 在账户页宽窄两态布局下均正确渲染。

### Requirement: NFR-4 质量门

- [ ] 新功能 SHALL 有对应测试(候选视图模型/收件箱存储状态机/聚合条 widget/托盘行);
  既有全量测试保持绿;analyze 基线零新增。

### Requirement: NFR-5 guest 兼容

- [ ] 提醒条/托盘行/收件箱 SHALL 在 guest 模式同样可用(本地扫描链路,与 reminder 同通道,
  无 server 依赖)。

## Scope boundary(排除及理由,均经挑战)

| 排除 | owner | 理由(辩护) |
|---|---|---|
| 启动弹窗提醒 | 用户(brainstorm) | 行业反模式,打断式;常显条零打扰已覆盖 |
| 新提醒来源(账单/订阅等) | 用户(brainstorm) | 逐源增量,DueSource 抽象已立,加源零返工 |
| 因常显层调整通知默认值(repeatHours 等) | 用户(grill #2) | 推/拉两通道语义不同;repeatHours 已是用户可调项 |
| 已读/未读全模型 | 用户(grill #5,裁 b) | 月个位数量级无「看到哪了」问题;小圆点是零成本折中 |
| 侧栏常驻项/标题栏铃铛入口 | 用户(一致性缝 #2) | 无待办时历史价值低,托盘唯二够用;不动 F29 标题栏控范围 |
| 收件箱历史上限清理 | 用户(一致性缝 #3) | 永久保留;月个位数量级无膨胀风险,对账回溯价值最大 |
| 历史区打小圆点 | 用户(一致性缝 #1) | 历史是档案;两区打点=已读包袱回潮 |

## Grill record

| # | 决策 | 挑战 | 辩护/裁决 |
|---|---|---|---|
| 1 | 条目直达 vs 统一跳 /debts 列表 | 直达需两数据源携带强类型路由目标(改 DueScheduleEntry 形态);跳列表零成本且 F37 已有着色 | 用户:直达。「看到→处理」压成两击,可完成性是常显层一半价值;跳列表则与债务页 F37 重复成信号灯 |
| 2 | 双通道叠加是否过度(6h 催办 × 常显条) | 催办重发的设计前提(无常显层)被抽掉一半 | 用户:同意不动。通知=推(人不在应用),常显=拉(打开才见);觉得吵调 repeatHours,不改默认 |
| 3 | 托盘行含金额并跟隐私开关? | 金额敏感度等同数据头两行,须跟开关 | 用户:不含金额。托盘行=环境层「有这事多急」,金额在常显条一步可达;笔数非金额承 F25 哲学 |
| 4 | 排除应用内通知历史中心 | ReminderLogs 已存(数据免费只差 UI);排除后回溯只能翻系统操作中心(不可靠) | **用户推翻排除**:「需要应用内的通知中心,这不应该是收件箱吗」→ 收件箱进 scope |
| 5 | 收件箱内容模型(窄台账/通用形/全抽象总线) | 窄做省但接新类型改语义;全抽象 YAGNI | 行业实践(量级决定模型:GitHub 式已读态=高量级,银行 alerts=低量级真相驱动)后,用户裁 **b**:通用形+本期单类型+type 字段预留;三态+新增小圆点;无已读态 |
| 6 | 一致性三缝(小圆点范围/无候选入口/历史留存) | 收件箱引入后的接缝矛盾 | 均按推荐确认:仅待处理区打点;托盘唯二入口;永久保留 |

## Feasibility

- **Technical:绿** —— 接缝全部现成:候选 = DueScanner 双源同一份;托盘行走 F25
  `headProvider` 注入缝 + 既有三触发刷新;还款对话框 `showCreditCardRepayDialog` 已有两处
  唤起先例;收件箱 = drift 增表(schema v10→v11,仅建表无损)。新增面仅三件:聚合条
  widget、收件箱页、收件箱存储。
- **Economic:绿** —— 中小体量单 feature;复用 v1.0.10(scanner/挂失)/ F37(着色桶)/
  F25(托盘数据头)三前作地基,无平行造轮。
- **Operational:绿** —— 纯本地零 server 改动;schema 增表无损迁移;guest 同链路可用;
  不新增权限/后台行为。
