维度 1：UI/UX 审计

对比消费级记账应用行业标准，分析账户修改功能的设计质量

🔴 严重问题

1. 复制功能实际上是坏的

代码位置：AccountsPage.tsx:375-379

handleEditSubmit 检查 'id' in data，但 Copy Sheet 提交时没有 id，所以 onSubmit 被调用但不执行任何 mutation — 用户以为提交了但其实什么都没发生。

对比 YNAB / Wallet

✓ YNAB 复制账户

新建一个与原账户设定相同的账户，名称自动加 "(Copy)" 后缀。用户可修改后保存。

✗ 当前实现

复制按钮打开表单但提交无响应，静默失败。用户完全不知道发生了什么。

2. 无法清除已填写的可选字段

问题：编辑账户时，如果用户想清空 account_number 或 institution，表单会将空字符串转为 undefined，后端收到 None 后跳过更新 — 原来的值永远无法清除。

行业标准：YNAB / GNU Cash 都支持清空可选字段。正确的做法是使用 null 表示"清除"，undefined 表示"不修改"。

3. 编辑模式下隐藏了关键信息

问题：编辑时 currency、type、ownership 都被锁定且视觉上变灰，但没有解释为什么不能修改。用户可能不理解为什么货币不能改。

行业做法：在不可编辑字段旁加一个 info icon 或 tooltip："货币一旦设定不可更改，因为会影响已有交易记录"。

🟡 设计缺陷

4. 两个创建入口不一致

AccountWizard（3步向导）vs NewAccountPage + AccountForm（单页表单）。

向导没有复用 AccountForm，而是自己维护了一堆 useState。两者的验证逻辑、默认值、字段分组完全不同。用户从不同入口进入会得到不同体验。

行业标准：通常只有一个创建入口，或两个入口共用核心表单组件。

5. 编辑表单位置不够直观

编辑通过右侧 Sheet 打开，但用户在列表页点击的是一个小铅笔图标。对比 Wallet / YNAB，点击账户名称直接进入详情页，编辑按钮在详情页顶部更显著的位置。

6. 缺少变更确认和差异视图

编辑保存时直接提交，不展示"你修改了什么"。对金融类应用来说，确认变更内容是重要的安全网。

🟢 做得好的部分

✓ 类型驱动的条件字段

CreditCard 显示信用额度/账单日/还款日，BorrowedIn/Out 显示利率，Prepaid 显示低余额阈值。条件字段展开逻辑正确。

✓ Ownership 分类合理

资产类 vs 收支类账户的分类方式符合中国会计准则中资产负债表和利润表的区分。

✓ 编辑时只读展示当前余额

在编辑模式中将当前余额设为只读展示，用户明确知道可改的是初始余额，不影响已有交易。
