维度 2：功能逻辑审计

深入分析更新流程、验证规则、边界情况与行业标准对照

🔴 严重问题

1. UpdateAccountDto 的 "None = 不修改" 设计缺陷

位置：account_service.rs:113-168

所有可选字段使用 if let Some(x) = dto.x 模式，意味着 None = "不修改"。但前端把空字符串当 undefined 处理，导致 无法清除已填写的可选字段。

行业标准：YNAB/GNU Cash 使用 null = "清除"，undefined = "不修改"。这是一种被广泛采用的 PATCH 语义模式（JSON Merge Patch RFC 7396）。

影响：用户填了卡号后无法删除；设了利率后无法清零。5个可选字段 account_number, institution, credit_limit, billing_day, payment_due_day, interest_rate 全部受影响。

2. 初始余额修改不触发余额重新计算

位置：account.rs:204-218

update_initial_balance 只修改 initial_balance 字段并发出 BalanceUpdated 事件。但前端显示的 "当前余额" = initial_balance + net_change（来自 transaction_entries）。

已有交易不受影响，但用户改初始余额后看到的余额会立即变化。没有任何确认或警告。这是一个金融安全问题——修改初始余额应该至少有一个确认提示，说明"这会改变你的账户余额"。

3. 更新时不检查名称唯一性

位置：account_service.rs:125

create_account 检查 find_by_name 防止重名，但 update_account 的 change_name 不做唯一性检查。用户可以把两个账户改成同名，造成混淆。

行业标准：大部分记账应用允许同名账户（因为不同类型下同名是合理的），但 YNAB 会警告。至少应提示。

🟡 设计缺陷

4. balance 校验逻辑有遗漏

validate_balance 禁止 Cash/Bank/Investment/BorrowedOut/Prepaid 初始余额为负。但用户后来通过交易让余额变成负数是完全可能的（已验证的 API get_account_balance 返回 initial_balance + net_change，不做范围检查）。

问题：初始余额的负数限制只降低了用户体验（新建现金账户不能输入为 -100 来表示已支出），但并不阻止最终余额为负。这个规则是否有意义需要重新思考。

5. low_balance_threshold 绕过了领域模型

位置：account_service.rs:163

account.low_balance_threshold = dto.low_balance_threshold 直接赋值字段，绕过了领域模型 setter 方法。对比其他所有字段都通过 update_* 方法设置。这违反了 DDD 原则——聚合根的所有状态变更应该通过方法。

6. AccountStatus/OpenedAt 未使用但有数据库迁移

schema 有 status 和 opened_at 列，域模型有 AccountStatus::Active/Archived/Hidden 枚举，但没有任何服务代码或 UI 操作它们。PostgreSQL 仓库更是完全忽略这些字段。DB CHECK 约束强制 status IN ('active','archived','hidden')，但代码始终硬编码 Active。

风险：用户无法归档或隐藏账户。

7. 复制功能逻辑缺陷

AccountsPage 中 handleEditSubmit 检查 'id' in data 来区分编辑与创建。但 Copy Sheet 使用同一 handler，而复制创建不会带 id，导致：

  • 复制操作永远不会调用任何 mutation
  • 没有新的 createMutation 被绑定到 Copy Sheet
  • updateMutation 被复用（但 copy 创建应该用 createAccount）

8. 预设模板名称硬编码中文

位置：account_service.rs:21-64

投资模板名称硬编码中文字符串 "股票账户"，与项目 i18n 规范冲突（CLAUDE.md 规定使用 i18n key）。前端 INVESTMENT_TEMPLATES 使用 t('accounts.templates.xxx')，但后端返回的是中文硬编码名。

🟢 做得好的部分

✓ 软删除保护

ensure_not_deleted() 在所有 setter 方法中被调用，防止修改已删除的账户。

✓ 三层验证架构

Zod（前端）→ Domain（后端聚合根）→ DB CHECK 约束。层次清晰，各有职责。

✓ touch() 自动更新元数据

每次字段修改都调用 touch() 更新 updated_at 并清除 synced_at，保证同步正确性。

✓ 删除使用乐观更新 + 回滚

deleteMutation 的 onMutate 先从缓存中移除，失败时回滚。用户体验更好。
