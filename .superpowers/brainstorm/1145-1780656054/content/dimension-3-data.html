维度 3：数据结构审计

分析 Schema、领域模型、DTO 层与行业标准对照

🔴 严重问题

1. DB 的 "loan" 类型值是幽灵数据

数据库 CHECK 约束允许 'loan' 作为 account_type 的值（历史遗留），但 Rust 枚举已经移除了 Loan 变体，只保留 BorrowedOut 和 BorrowedIn。

风险：如果数据库中存在旧的 'loan' 行，row_to_account 会返回 Decode error，导致整个列表页崩溃。

行业标准：数据库枚举应与代码枚举严格一致。要么在 DB 中把 'loan' 迁移为 'borrowed_in'，要么在 Rust 中做 fallback 映射。

2. Decimal 字段全用 TEXT 存储

initial_balance、credit_limit、interest_rate、low_balance_threshold 在 DB 中都是 TEXT 或 CAST(...AS TEXT)。SQL 查询中用 CAST(initial_balance AS TEXT) 来保持精度。

问题：

  • 无法在 DB 层做数值比较/排序/聚合（如 "找余额 > 10000 的账户"）
  • 每次读写都需要 Decimal ↔ String 互转，增加出错面
  • 无法在 DB 层约束负数（靠代码约束）

行业标准：SQLite 支持 DECIMAL（实际存储为整数分），或使用整数分值（如 YNAB 存储所有金额为整数分）。

3. AccountDto 缺少低余额阈值和状态字段

AccountDto（返回给前端的主要数据结构）缺少：

  • low_balance_threshold — 前端在列表中用到了 Low Balance 警告！
  • status — 无法区分 Active/Archived/Hidden
  • opened_at — 无法显示开户日期

但前端 AccountsPage 代码中有 account.low_balance_threshold 的引用（第154行），说明前端和后端的 DTO 不同步 — 前端期望的字段后端没有序列化。

这可能是一个实际 bug：低余额警告可能从不工作，因为 DTO 没有包含这个字段。

🟡 设计缺陷

4. created_at 是假的

位置：account_dto.rs:84-93

AccountDto::created_at = account.sync_metadata.updated_at — 没有单独的 created_at 字段。

每次更新账户后，created_at 和 updated_at 值相同。数据库 schema 也只有 updated_at，没有 created_at。

行业标准：几乎所有金融产品都区分创建时间和最后修改时间。

5. billing_day/payment_due_day 类型不一致

整条链路的类型转换：

DB INTEGER → Repository i64 → u8 → Aggregate u8 → DTO u8 → 后端 Update i32 → 前端 string

前端发送 "5"（字符串），后端接收 i32，领域模型用 u8，数据库是 INTEGER。类型链过长，每层都要转换。

风险：前端发送 billing_day: "0" 或 "32"，Zod 验证会通过（字符串非空+合法），但领域模型会拒绝。validation 位置不一致。

6. UpdateAccountDto 中 currency_code 是多余的

位置：account_dto.rs:30

UpdateAccountDto 包含 currency_code: Option<String>，但服务层完全忽略它（update_account 使用 account.currency_code 重建余额）。领域模型 update_currency_code() 永远返回 CurrencyMismatch 错误，是不可变字段。

这个字段的存在是误导性的 — 如果前端误发了它，没有效果也没有错误提示。

7. PostgreSQL 仓库严重不完整

account_repository_postgres.rs 是 #![allow(dead_code)]，不解析 account_number, institution, credit_limit, billing_day, payment_due_day, interest_rate, low_balance_threshold 等字段。

如果将来启用 PostgreSQL 同步，所有这些字段会丢失。

8. parent_id 自引用没有循环引用保护

数据库有 parent_id REFERENCES accounts(id)，但没有任何代码阻止 A→B→A 循环引用或自引用。也没有递归查询来构建账户层级。

实际上前端也完全没有使用 parent_id 来展示层级关系 — 它是一个"写了但没用"的字段。

🟢 做得好的部分

✓ 软删除设计正确

deleted_at 时间戳模式，查询时 WHERE deleted_at IS NULL 过滤。find_all_including_deleted 为同步保留能力。

✓ SyncMetadata 内聚

updated_at, deleted_at, device_id, synced_at 封装为 SyncMetadata 值对象，而非散落在字段中。

✓ 余额计算分离

compute_balances_for_all_accounts 集中查 transaction_entries，而非逐账户查询，效率好。

✓ Money 值对象保证币种一致性

Money { amount: Decimal, currency_code: String } 保证金额和币种不分离，避免"1000 是什么货币"的歧义。
